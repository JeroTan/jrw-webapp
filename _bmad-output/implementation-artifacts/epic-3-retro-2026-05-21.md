## Successes and Strengths

1. **100% story completion** — All 10 stories delivered with full vertical slices (domain, repository, service, controller, routes, tests, UI).

2. **Review process caught significant bugs** — 20+ review patches across the epic. Highlights:
   - Story 3.8: Snapshot build endpoint bypassed brand membership guard entirely
   - Story 3.5: 6 patches including R2 rollback gaps, provider error leakage, orphaned objects
   - Story 3.6: stock_version concurrency guards, archive state DTO mapping, audit event gaps
   - Story 3.7: Stale status transitions, readiness checker counting archived categories

3. **Cross-story lesson handoff chain** — Each story documented and carried forward lessons from the previous story's review findings. 3.1 slug auto-rename bug → 3.2 explicit error return → 3.3 brandless clarity.

4. **Concurrency groundwork established** — `stock_version` compare-and-swap pattern in Story 3.6 sets the foundation for Epic 5's Durable Object inventory reservation.

5. **Test suite grown 4x** — From 122 to 500+ tests across 77 files. Targeted-test pattern (changed surfaces only during dev, full suite by MR. JRW) consistent across all 10 stories.

6. **Consistent architecture** — Every story followed Route → Controller → Service → Domain/Repository pattern without deviation.

7. **Zero production incidents** — Clean epic with no runtime failures.

8. **Shared primitives investment paid off** — Story 3.0's ViewToggle, SearchInput, ResourceCard, ResourceList, PageToolbar reused across Stories 3.1-3.9.

9. **Quick in-retro fix** — ViewToggle size inconsistency between /admin/brands and /admin/products identified and fixed during retro (parent grid layout mismatch).

## Challenges and Growth Areas

1. **Permission guard gaps on new endpoints (recurring)** — Stories 3.5, 3.6, 3.7, and 3.8 each had new endpoints missing brand membership or RBAC checks. The 3.8 snapshot endpoint bypassed brand membership entirely.

2. **Concurrency and race conditions** — Stories 3.5 (R2+DB rollback), 3.6 (stale stock_version), and 3.7 (stale status transitions) all had race-condition bugs. Pattern escalated in severity from 3.5 to 3.6 before being tamed.

3. **Story 3.5 peak complexity** — First infrastructure story with real provider integration (R2). 6 review patches was the most of any story. R2 upload + DB insert without transaction-safe rollback was the root cause.

4. **Price column type inconsistency** — `price` column is `real` (float) in DB while architecture requires integer centavos. Mapped at repository boundary in 3.4, same issue in 3.8 for `price_at_purchase`. Migration deferred.

5. **Non-TTY Drizzle prompt** — Every schema change hit Drizzle Kit blocking on non-interactive prompts. Worked around with manual SQL. Fragile and error-prone.

6. **Lesson handoff had gaps** — While most lessons carried forward, the stale-transition concurrency fix from 3.6 didn't make it to 3.7's status mutation logic.

7. **Editor reset on async data (Story 3.3)** — Product editor reset user edits when organization data arrived asynchronously. Fixed in review.

## Key Insights

1. **New endpoints = new guard gaps** — Happened 4 times across the epic. Brand membership and RBAC checks are not part of the automatic developer workflow.

2. **Complex integration surfaces need more structural prep** — R2, provider error handling, and rollback complexity in 3.5 was underestimated. An infrastructure checklist would have caught most gaps before review.

3. **Deferred migrations accumulate** — `price` column type, Drizzle prompt, remote migration application — each deferral adds risk to later work.

4. **Cross-story lesson chain works but has gaps** — Explicit documentation between stories prevented most regressions but not all (stale transitions from 3.6 to 3.7 slipped through).

## Post-Retro Fix Applied During Retrospective

### Fix 1: ViewToggle Size Inconsistency
- **Problem**: ViewToggle button in /admin/products rendered larger than in /admin/brands, despite being the same shared component.
- **Root cause**: In ProductListDashboard.tsx, the ViewToggle was inside a `.jrw-control-grid` div with `grid-template-columns: repeat(auto-fit, minmax(260px, 1fr))`. The grid stretched the ViewToggle to fill its cell (≥260px), overriding the component's natural `inline-grid` sizing (~176px for two 88px buttons).
- **Fix**: Restructured the filter toolbar to use the `actions` slot of `PageToolbar` (matching the BrandList pattern), which uses flexbox `justify-content: flex-end` and `gap: var(--jrw-space-xs)` — no stretching.
