## Successes and Strengths

1. **11/11 stories delivered** — Full storefront and cart implementation from shell through product detail composition.

2. **Public API architecture established** — Story 4.1 correction set the canonical Route -> Controller -> Service -> Repository pattern with TypeBox schemas, public auth metadata, safe envelopes, and D1 read isolation. Stories 4.2, 4.3, 4.4, 4.5, and 4.11 all reused it.

3. **Review process caught real bugs** — 85+ patches across stories caught: unpublished data leakage (4.5), hydration races (4.5), accessible label gaps (4.11), focus trap issues (4.7), visual contract violations (4.9).

4. **Playwright browser QA introduced** — Story 4.5 added dedicated Playwright config, route mocking, and browser tests. Caught a critical hydration race that unit tests missed. Stories 4.6 and 4.7 expanded with axe accessibility scans and shared QA helpers.

5. **TDD discipline maintained** — Stories 4.2, 4.5, 4.7, 4.8, and 4.9 wrote failing tests first. Three-layer testing (domain -> server -> UI) consistent across most stories.

6. **MR. JRW correction pass on 4.11** — Direct visual refinements applied after initial implementation: media border removed, background tokens corrected, price sizing adjusted, variant chips made obvious, buy/cart/share layout fixed.

7. **Review patches consistently improved quality** — Every story averaged 5-10 patches finding real issues. No story was accepted without at least one correction.

## Challenges and Growth Areas

1. **Public copy leaking internal language** — 4 stories (4.1, 4.2, 4.3, 4.5) had review findings where UI or API responses exposed 'story', 'placeholder', or admin-internal terms to users.

2. **Server data leaking to public boundaries** — 4.2 exposed unpublished product counts, 4.5 leaked unpublished product data, 4.11 exposed raw stock counts through max quantity.

3. **Hydration race conditions** — The direct `/checkout` hydration race between SSR server data and browser cart store (4.5) required deferred-first-validation logic. This pattern will recur in Epic 5.

4. **Responsive QA gaps** — Multiple stories had viewport/browser QA not run or partially run. 4.6 review found category/brand detail routes were not checked at required widths.

5. **Dirty worktree test pollution** — 4.5 and 4.6 both blocked on unrelated uncommitted changes breaking `npm run build-test`. Worked around with targeted suites.

6. **Post-done stabilization** — Stories 4.4 (10+ stabilization items) and 4.5 (code-review patches after done status) required follow-up. Definition of Done may need explicit stabilization phase.

7. **Playwright dependency fragility** — 4.11 blocked on `Cannot find package '@playwright/test'` despite being installed in the project.

## Key Insights

1. **AI handles architecture and logic; human handles feel** — MR. JRW manually refined UI across multiple stories. The visual decisions (spacing, layout, token selection, interactive feel) required human judgment that automated processes cannot replace.

2. **Browser QA is essential for stateful UI** — The hydration race in 4.5 was invisible to unit tests. Playwright caught it immediately. Every story with interactive state needs browser-level verification.

3. **Public boundary discipline is hard to automate** — Server data leaking to public endpoints happened in 3 separate stories despite guard checklists. Each was caught by review, not by tests.

4. **Single canonical architecture accelerates execution** — After the public API pattern was established (4.1), subsequent stories reused it without deviation. No new endpoint patterns were invented mid-epic.

5. **Visual fidelity requires hands-on stakeholder passes** — The MR. JRW correction on 4.11 identified 8+ visual issues that automated tests and review did not catch. Plan for this in every UI-heavy epic.
