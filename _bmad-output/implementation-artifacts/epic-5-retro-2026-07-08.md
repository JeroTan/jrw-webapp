## Successes and Strengths

1. **Server authority stayed intact**
   Payment success never trusts redirect params or browser state. Webhook and return-status fallback both reconcile from JRW server/provider truth.

2. **Inventory safety became concrete**
   Story 5.2 added guarded stock decrement, active reservation uniqueness, retry-safe reservation behavior, and 100-attempt oversell coverage. Story 5.6 added release ledger semantics for terminal/stale payment paths.

3. **Idempotency moved from checklist to behavior**
   Duplicate reservation retries, duplicate PayMongo events, duplicate paid returns, refreshes, terminal payment release, and payment emails now have explicit tests or repository guards.

4. **PayMongo boundary hardened**
   Frontend never calls PayMongo directly. Checkout URL validation rejects untrusted hosts. Provider payloads, card data, checkout URLs, signatures, secrets, tokens, contact PII, and raw responses stay out of public surfaces.

5. **Review process caught high-value bugs**
   Major fixes included atomic reservation persistence, mutation-time stock predicates, DO payment serialization, duplicate paid webhook retry, stale email-send reclaim, terminal payment normalization, and release retry visibility.

6. **Epic 4 lessons mostly applied**
   Hydration/cart-state concerns were addressed through checkout state gates and cart fingerprint reset. Public data leak guardrails were reinforced through endpoint guard checklists, safe DTOs, scrubbers, and tests.

7. **Full regression recovered by Epic close**
   Earlier broad-suite instability appeared during 5.3, 5.5, and 5.6, but Story 5.7 recorded full regression passing: 131 files and 869 tests.

## Challenges and Growth Areas

1. **Concurrency and idempotency were repeatedly underestimated**
   Review patches clustered around race conditions: active reservation retry, stock mutation atomicity, payment creation serialization, duplicate webhook paths, and terminal release retries.

2. **Provider reality required fallback design**
   Development lacked webhook-secret success path in one observed return. A paid PayMongo session could leave JRW pending until `spec-payment-return-provider-reconciliation.md` added backend-only provider fallback.

3. **Remote schema drift affected UX**
   Payment-return receipt work found missing remote development migrations. The fix was correct, but Epic 6 should treat remote D1 schema verification as part of readiness for order work.

4. **Full-suite stability created noise**
   Several stories had targeted tests passing while broad suite output failed, timed out, or lacked actionable diagnostics. `spec-stabilize-vitest-worker-lifecycle.md` is still in review.

5. **Receipt/status browser QA lacks fixture support**
   Story 5.7 documents a responsive/manual viewport QA blocker because no seeded browser payment-return fixture exists. Component tests covered markup and class contracts, but live checkout receipt inspection remains weaker than desired.

6. **Order model still carries legacy shape**
   Deferred work notes legacy `orders.status` and `orders.total_amount real` remain for backward compatibility. Epic 6 order APIs must use canonical `payment_status`, `fulfillment_status`, and centavos fields.

7. **Order snapshots miss frozen image references**
   `checkout_payment_items` does not store frozen image reference yet, so `order_snapshots.image_r2_key` remains `null`. Epic 6 order history needs either a schema fix or an explicit fallback.

## Key Insights

1. **Payment flow needs two authorities, not one**
   Webhook remains primary, but return-status fallback is necessary when webhook delivery or secret setup is incomplete. Both paths must converge on the same idempotent order confirmation.

2. **Idempotency belongs at persistence boundary**
   Service checks helped, but strongest fixes came from unique indexes, guarded updates, payload hashes, release ledgers, and repository fallback to existing confirmed records.

3. **Provider state is not enough without local invariants**
   PayMongo paid status can start reconciliation, but local payment row, checkout attempt, reservation, and frozen payment items decide what JRW can safely confirm.

4. **UI receipt needs real server fixtures**
   Receipt/status UX depends on paid, pending, failed, expired, cancelled, and unknown server states. Without seeded fixtures, visual QA becomes component-only and misses integrated browser behavior.

5. **Order work starts with schema truth**
   Epic 6 should not build admin/customer order surfaces on legacy order fields or incomplete snapshots.
